Phase 2 – Sprint 3

Chunk 8 – Announcements Row-Level Security (RLS)

# Goal

Implement Row-Level Security for Announcements using the new Resource Authorization Policy framework.

This chunk serves as the first real-world consumer of the policy abstraction introduced in Chunk 7.

Announcements are COURSE-SCOPED resources.

Authorization must be enrollment-based.

# Existing Infrastructure

Already available:

* ScopeContext
* SessionEnricher
* childCourseIds
* enrolledCourseIds
* CourseScopeValidator
* applyCourseScopeFilter()
* ResourceScopePolicy
* NotesScopePolicy
* AssignmentScopePolicy
* AssessmentScopePolicy

Reuse existing infrastructure.

Do not duplicate authorization logic.

# Authorization Rules

Admin

* Global access

Teacher

* Global access

Student

* Can access announcements where:

```text
announcement.course_id IN scope.enrolledCourseIds
```

Parent

* Can access announcements where:

```text
announcement.course_id IN scope.childCourseIds
```

Announcements are COURSE-SCOPED.

Never use student ownership checks.

Always authorize using course access.

# Endpoints In Scope

Implement RLS for:

```ts
listAnnouncements()
```

and

```ts
getAnnouncementById()
```

Only these endpoints.

Do not modify create/update/delete behavior.

Do not implement portal-specific routes.

# Layer 2 Requirements

Apply query-level filtering.

Use:

```ts
applyCourseScopeFilter(...)
```

Behavior:

Admin:

* no filtering

Teacher:

* no filtering

Student:

* filter by enrolledCourseIds

Parent:

* filter by childCourseIds

Filtering must occur in SQL query construction.

No in-memory filtering.

# Layer 3 Requirements

Implement post-fetch validation.

For:

```ts
getAnnouncementById()
```

Flow:

1. Fetch announcement
2. Validate existence
3. Validate course access
4. Return result

Example:

```ts
validateCourseAccess(
  scope,
  announcement.courseId
);
```

Maintain defense-in-depth.

# Announcement Policy

Create:

```ts
AnnouncementScopePolicy
```

Implement:

```ts
applyFilter()
validateAccess()
```

Reuse existing course-scoped authorization patterns.

Avoid resource-specific authorization code in services.

Services should delegate authorization decisions to the policy.

# Soft Delete Requirements

Ensure soft delete behavior remains enforced.

Deleted announcements must not be visible.

Expected:

Deleted announcement:

```http
404 Not Found
```

not:

```http
403 Forbidden
```

Verify only authorized announcements are returned.

Student:

Course A announcement => visible

Course B announcement => hidden

Parent:

Child course announcement => visible

# Layer 3 Security Tests

Verify direct ID access protection.

* authorized announcement => 200

Parent:

* authorized announcement => 200

# IDOR Tests

Explicitly verify enumeration resistance.

Examples:

```http

```
